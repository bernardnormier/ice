# Ice C# Dead Code Report

**Date:** 2026-06-13
**Scope:** `csharp/src` (the Ice for .NET assemblies, the IceBox/IceGrid/IceStorm/Glacier2/discovery components, and the `ZeroC.Ice.Slice.Tools` MSBuild tasks)
**Target framework:** `net8.0` (the `ZeroC.Ice.Slice.Tools` task assembly targets `netstandard2.0`)
**Permalink base:** all source links below are pinned to commit [`2f1d39c`](https://github.com/zeroc-ice/ice/tree/2f1d39c427a5a6dcbee73208d9536e760e322487/csharp) so line numbers stay stable even as `main` moves.

---

## How this was produced

Three complementary methods, the same approach used for the C++ audit, adapted to C#:

1. **Full Debug build** (`dotnet msbuild msbuild/ice.proj`). The build is **warning-clean**, and — critically — the projects set `AnalysisMode=All`, `WarningLevel=4`, and `TreatWarningsAsErrors=true` ([msbuild/ice.common.props](https://github.com/zeroc-ice/ice/blob/2f1d39c427a5a6dcbee73208d9536e760e322487/csharp/msbuild/ice.common.props)). That means every unused **`private`/`internal`** member — `CS0169` (unused field), `CS0414` (assigned-but-unused), `CS0649` (never-assigned), `IDE0051` (unused private member), `IDE0052` (unread private member) — **fails the build**. Because the build passes, the truly-private/internal dead-code surface is **provably empty**.
2. **Repo-wide static cross-referencing** of every symbol defined under `csharp/src`, partitioned across the codebase. For each candidate, references were counted across the *entire* C# tree (`csharp/src` **and** `csharp/test`, including the generated Slice code).
3. **Independent spot-verification** of every high-value finding (re-greps for interface membership / `override`, overload resolution, and reflective binding).

### The consequence: all dead code here is "public-but-internal"

Point 1 above is the key to reading this report. Since the compiler+analyzers already guarantee there are **no** unused `private` or `internal` members, the only dead code that *can* exist is in members the analyzers don't inspect: **`public` members that are logically internal**. Per your guidance:

> All code in namespace `Ice.Internal` is internal (regardless of access modifier). Same for `UtilInternal`.

These namespaces (and the internal transport plumbing inside `Ice.SSL`) are full of `public` types whose visibility is an artifact of cross-assembly access, not a public-API contract. A `public` member there with **no reference anywhere in the C# tree** is dead — the analyzers can't see it precisely *because* it's `public`. That is exactly where every Category-A finding below lives.

### Multi-platform note

Unlike the C++ tree, the C# sources contain **zero `#if` conditional compilation** and a single target framework (`net8.0`) — there are no platform/runtime branches to reason about, so a clean local build sees all of the code. (See Category D.)

### Excluded from the audit (not dead, but not in scope)

- **Generated Slice code** — everything under `*/generated/` and `*/obj/` (carries the `<auto-generated>` banner). These are regenerated from `.ice` files. They were **excluded as a source of candidate symbols** but **searched for usages** — generated code is the primary consumer of `Ice.Internal`, so a symbol used only by generated code is **live**.
- **Reflection / dispatch / plugin entry points** — servant dispatch (`iceD_*`), Slice marshaling (`ice_read`/`ice_write`), instrumentation getters bound via `Type.GetMethod("…")`, plugin/service/logger classes loaded by assembly+class-name strings from config, and MSBuild task classes invoked by name. Verified and **not** reported.
- **Polymorphic members** — interface implementations, `virtual`/`abstract`/`override` members, operators, `Equals`/`GetHashCode`/`ToString`/`Dispose`/`IComparable`/`IEquatable`. Reachable indirectly; excluded.
- **Test usage counts as live** — symbols referenced only from `csharp/test` are **not** dead.

**Headline:** The C# codebase is very clean. Because CI treats all analyzer warnings as errors, there is **no** dead private/internal code at all. The findings are two-dozen small `public` members in the logically-internal namespaces — unused accessors, scalar readers, and convenience overloads that the analyzers can't flag because the access modifier says `public`. All are low-risk deletions.

## Category D — Conditional / platform dead code

**Empty — a clean result.** The C# sources contain **zero `#if` / `#elif` conditional compilation directives** and build against a single target framework (`net8.0`; `netstandard2.0` only for the `ZeroC.Ice.Slice.Tools` MSBuild task assembly). There are no legacy-framework, legacy-runtime, or platform branches that never compile. The only build constants in play are `DEBUG`/`TRACE`, used by the build configuration, not gated source. (This mirrors the C++ result, where the equivalent legacy-platform category was also effectively empty.)

## Suggested next steps

1. **Low-risk cleanup (Category A, 23 symbols):** delete the unused `public`-but-internal accessors, scalar readers, convenience overloads, and the two unused `OutgoingAsyncBase` state constants. Each is an independent, self-contained deletion; none is reachable on any path. Recommend grouping by file (`ByteBuffer.cs`, `ThreadPool.cs`, `StringUtil.cs`, `SSLEngine.cs`) so each diff is easy to review.
2. **Decision for the team (Category B):** keep or drop `SliceCompilerTask.GeneratedExtensions` — it's unused but is part of a subclassable base's `protected` surface.
3. **API decisions (Category C):** the 11 public-API entries are deprecate-vs-keep calls. Several (`generateUUID`, `IceBox.FailureException.reason`) are already intentional back-compat; the asymmetric ones (`NativePropertiesAdmin.removeUpdateCallback` with no caller while `addUpdateCallback` is used) may be worth a closer look.
4. **Optional hardening:** several Category-A members could alternatively be made `internal` rather than deleted — at which point the analyzers (`IDE0051`) would catch any future disuse automatically. Tightening visibility on `Ice.Internal`/`UtilInternal` types where cross-assembly access isn't actually needed would shrink the "public-but-internal" blind spot going forward.

### Caveats / known coverage gaps

- Findings reflect the source tree at commit [`2f1d39c`](https://github.com/zeroc-ice/ice/tree/2f1d39c427a5a6dcbee73208d9536e760e322487/csharp) (2026-06-13).
- The `private`/`internal` dead-code surface is **provably empty** (CI fails on the relevant analyzer warnings), so this audit is necessarily limited to `public` members; that is also why it is high-confidence — the only place dead code can hide is the public-but-internal surface, which was swept exhaustively.
- Reflection and Slice-runtime dispatch were handled by checking generated code and reflective `GetMethod`/class-name-string usages, not by an automated reachability tool. Confidence is per-symbol and evidence-based (reference counts + dispatch/override/reflection checks). Treat the list as a high-quality candidate set to confirm in review, not an auto-delete list.
