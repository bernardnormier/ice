# Ice C++ Dead Code Report

**Date:** 2026-06-13
**Scope:** `cpp/` (libraries, services, and the `slice2*` translators)
**Supported build matrix (per `cpp/BUILDING.md`):** C++17 — Clang/macOS, Clang/iOS, GCC/Linux, Visual Studio 2022 (MSVC)/Windows
**Permalink base:** all source links are pinned to commit [`2f1d39c`](https://github.com/zeroc-ice/ice/tree/2f1d39c427a5a6dcbee73208d9536e760e322487/cpp) so line numbers stay stable even as `main` moves.

---

## How this was produced

Four complementary methods, so that no single platform's view or single tool's blind spot drives a deletion decision:

1. **Full macOS build** with the project's default flags (`-fvisibility=hidden -Wall -Wextra -Wshadow -Wredundant-decls`). The build is **warning-clean** — `-Wunused-function`/`-Wunused-variable` reported **zero** unused `static`/anonymous-namespace functions or variables, so translation-unit-local dead code is essentially nil.
2. **Repo-wide static cross-referencing** of every symbol defined under `cpp/src`. For each candidate, references were counted across the entire repo — `cpp/src`, `cpp/include`, `cpp/test`, `cpp/tools`, the `.ice` files, **and the C++ source of the language mappings that link the Ice C++ runtime** (`python/modules/IcePy`, `php/src`, `ruby/src/IceRuby`, `matlab/src`, and the `swift/src/IceImpl` glue). These mappings call both the public API *and* internal headers (e.g. `Ice/OutputUtil.h`, `IceInternal::Options`), so they are first-class callers. A symbol is reported only when its sole references are its own declaration/definition.
3. **Linker symbol-table (`nm`) cross-TU analysis** of the compiled object files. A function declared in an internal header and defined out-of-line in a `.cpp` is a global `T` symbol; if it is referenced (`U`) by no other translation unit it is dead or used only within its own `.cpp`. This pass works on **mangled** symbols, so it is immune to the name-collision masking that defeats text search (see *Methodology notes*), and it is the authoritative method for the exported-internal-header category. (The language-mapping extensions are not compiled in this tree, so their object files are absent from the symbol-table set — method 2's source search is what covers their calls into the runtime.)
4. **Independent per-symbol verification** of every finding — re-checking virtual/override status, base-class declarations, overload resolution, qualified/bare/template-wrapper call forms, reflective/dispatch usage, and platform guards.

### Multi-platform guard rule

Because the macOS build cannot compile Windows/Linux-only code, a symbol used **only** inside a platform guard (`_WIN32`, `__linux__`, `ICE_USE_IOCP`/`SCHANNEL`/`EPOLL`/`KQUEUE`/`SECURE_TRANSPORT`/`OPENSSL`/`CFSTREAM`, iOS `TARGET_OS_IPHONE`) is treated as **live** — it is exercised on another supported platform. Nothing is flagged dead unless it is unused on **every** supported platform. Windows-only findings (marked below) could not be compile-verified on this machine and carry that caveat.

### Excluded from the audit (not dead, but not in scope)

- **Generated parser files** — `Grammar.{y,cpp,h}`, `Scanner.{l,cpp,h}` (Bison/Flex output) and everything under `*/generated/`. Regenerated by tooling; their internal helpers (`fatalError`, `initScanner`, `parse*QuotedString`, …) are generator boilerplate.
- **Slice-dispatched servant methods** — a method whose name matches a Slice operation is invoked by the Ice runtime via dispatch, with no C++ call site. Verified against the relevant `.ice` files and **not** reported.
- **Virtual overrides, plugin/`extern "C"` factories, streaming `operator<<`, exception types** — reachable indirectly; excluded or downgraded to *suspect*.

## Category B — Suspects (human review recommended)

These look dead but have a subtlety that warrants a human decision before removal.

- **`SecureTransport::getCertificateProperty` (public overload)** — [SecureTransportUtil.cpp:210](https://github.com/zeroc-ice/ice/blob/2f1d39c427a5a6dcbee73208d9536e760e322487/cpp/src/Ice/SSL/SecureTransportUtil.cpp#L210) (decl [.h:20](https://github.com/zeroc-ice/ice/blob/2f1d39c427a5a6dcbee73208d9536e760e322487/cpp/src/Ice/SSL/SecureTransportUtil.h#L20)). A byte-for-byte twin exists in an anonymous namespace at [SecureTransportUtil.cpp:84](https://github.com/zeroc-ice/ice/blob/2f1d39c427a5a6dcbee73208d9536e760e322487/cpp/src/Ice/SSL/SecureTransportUtil.cpp#L84). The four unqualified call sites in the same TU bind to **one** of them; by C++ lookup rules the anon-ns one wins, making the public definition the redundant/dead copy — but the resolution is subtle. *Safe cleanup: drop the public definition + its header decl, keep the anon-ns twin.*
- **`DistinguishedName` relational operators** — `operator<`/`>`/`<=`/`>=`/`!=` at [DistinguishedName.h:74-84](https://github.com/zeroc-ice/ice/blob/2f1d39c427a5a6dcbee73208d9536e760e322487/cpp/src/Ice/SSL/DistinguishedName.h#L74-L84) / [.cpp:23](https://github.com/zeroc-ice/ice/blob/2f1d39c427a5a6dcbee73208d9536e760e322487/cpp/src/Ice/SSL/DistinguishedName.cpp#L23). No `DistinguishedName` is ever sorted, so these are unused — but `operator==` **is** live (`cpp/test/IceSSL/configuration/TestI.cpp`). They form a complete relational interface; **recommend keeping** for API symmetry.

## Methodology notes & confidence

- **Why a symbol-table pass, not just text search.** Several findings (`ProtocolInstance::defaultEncoding`, `Slice::Enumerator::hasExplicitValue`) are dead *methods* whose name collides with a heavily-used *field* or sibling — e.g. the method `defaultEncoding()` vs. the field `DefaultsAndOverrides::defaultEncoding`, and the singular `Enumerator::hasExplicitValue()` vs. the plural `Enum::hasExplicitValues()`. A bare-name grep reads these as "used." The `nm` pass works on mangled symbols and is immune to that masking; it is the authoritative method for exported internal-header functions and surfaced these where text search alone did not.
- **The symbol-table pass is complete but not precise.** It cannot *miss* a dead non-virtual out-of-line function, but it flags false positives that must be discarded by a per-candidate read of every call form. The recurring false-positive shapes (all verified and excluded here): **inline functions** used within their own `.cpp` (no out-of-line definition to scan — e.g. `checkIdentity`, `notConnected`, `valueIdToString`); **virtual overrides whose `final` definition lives in a `.cpp`, not a header** (e.g. Glacier2's `createFilterManager` pair, dispatched via a pure-virtual base); **qualified static calls** (`StopCommand::isStopped(_state)`); **public-header template-wrapper calls** (`uncheckedCast<Prx>(_createProxy(...))`); and **generated Flex/Bison parser internals**.
- **The language mappings are in-repo callers.** `cpp/` is not the only C++ in the repository: the Python (`python/modules/IcePy`), PHP (`php/src`), Ruby (`ruby/src/IceRuby`), MATLAB (`matlab/src`), and Swift (`swift/src/IceImpl`) mappings are ~130 C++ files that link the Ice C++ runtime and call both its public API and its internal headers. They are **not built in this tree** (no object files), so the symbol-table pass cannot see them — only the source search reaches them. Including them corrected four findings that looked dead in `cpp/` alone: `OutputBase::setUseTab` (called from the Ruby mapping), `ObjectAdapter::findByProxy` and `Properties::getCommandLineOptions` (called from several mappings), and `InputStream::getClosure`/`setClosure` (called from IcePy/php/ruby — while the byte-identical `OutputStream` pair is genuinely unused). Any future pass over `cpp/` must search these directories.
- **Confidence is per-symbol and evidence-based** (reference counts incl. generated code + dispatch/override/overload/guard checks), not the output of an automated whole-program reachability tool. Treat the list as a high-quality candidate set to confirm during code review, not an auto-delete list.

### Caveats / known coverage gaps

- Findings reflect the source tree at commit [`2f1d39c`](https://github.com/zeroc-ice/ice/tree/2f1d39c427a5a6dcbee73208d9536e760e322487/cpp) (2026-06-13).
- The macOS build cannot compile Windows-only or some Linux-only paths; those branches were judged by static cross-reference + guard analysis, not by compilation. Windows-only IceSSL findings are flagged accordingly.
- The `nm` cross-TU pass covers code that the macOS build compiles; it does not see Windows/Linux-only object files. The default build is optimized, but the exported-internal-header category (declared in a header, defined out-of-line in a `.cpp`) cannot be inlined across translation units without LTO, so the symbol-table view is reliable for it, and the per-candidate source check is inlining-immune regardless.
- The language-mapping C++ (`python/modules/IcePy`, `php/src`, `ruby/src/IceRuby`, `matlab/src`, `swift/src/IceImpl`) was searched as a **caller** of the Ice runtime, which is what corrected the four findings above. Its **own** internal dead code was **not** audited here — these directories are out of the `cpp/` scope of this report and would warrant a separate per-mapping pass.
